## How the pieces talk

- Pages are server components that check the session (the proxy now covers `/feed`, `/tracker`, `/settings` and hands the layout the requested path for its login redirect via `x-redlance-path`, always overwritten by the proxy and filtered by `safeNextPath`). First paint reads data server-side; client components then call `/api/v1` with `apiFetch`.
- The list and the match page are separate trees under the feed layout. A status change on either side is announced on a window event (`feed-events.ts`), with the whole match attached, so a dismissed-then-restored gig goes back into the list.
- The list drops responses from an older filter set (a generation counter), rolls back an optimistic status only if nothing changed it since, and only looks for new gigs once it has loaded.
- Idempotency keys are tied to the exact request (draft for this match, or this rewrite of this version) and reused only after a network failure.
- Draft edits and what was marked sent are kept per match for the browser session, so moving between matches keeps them; closing the tab with unsent edits asks first.

## Faster feed: data arrives with the page (2026-10-21)

- **Drafts with the match page.** `feed/[matchId]/page.tsx` reads the match, credits, `listVersions` and `sentKindsForMatch` in parallel and passes `initialVersions` and `loadedAt` (epoch ms) down; the composer starts with them (no grey placeholder). Without `initialVersions` it still fetches `GET /api/v1/drafts?matchId=` itself. That route now also returns `sentKinds` (the reply kinds already marked sent for the match's post).
- **First list page on the server.** `feed/layout.tsx` calls `loadInitialFeed` (`server/feed-initial.ts`): it reads the filters from the query string in `x-redlance-path` (layouts get no `searchParams`; the proxy sets the header on every request, overwriting any client value, and `searchParamsFromRequestPath` runs it through `safeNextPath`), parses them with `filtersFrom` against the profile's categories, and loads the first page with `feedPage` + `toFeedResponse`, the code behind `GET /api/v1/feed` (`FEED_PAGE_SIZE` = 25, shared with the client). `FeedList` takes `initial` and starts `ready` only when the URL's filters equal `initial.filters` (`startState`); it skips the first fetch for that one query. The layout is shared and not re-rendered on child or search-param navigation, so after a client-side filter change it fetches as before. If the read fails it is logged (`getLogger().error`, "feed layout: first page read failed"), `initial` is absent and the list fetches itself.
- **No list read when the browser already has the layout.** A full prefetch of a match page renders the feed layout again once Next's cached copy of the layout segment has expired, which would run `feedPage` for nothing. Next 16.3 sends **no** `Next-Router-Prefetch` header on a full prefetch (`FetchStrategy.Full` in `segment-cache/cache.js` sets none; only the route-tree and loading-boundary prefetches send `1`), so the server can't spot it by that header. Instead `clientHasLayout` reads Next's `next-router-state-tree` request header (URI-encoded JSON of the route tree the client asks about) and skips the read when the tree holds `["", "(app)", "feed"]`: a prefetch from the list (its tree is the target route) or a navigation/refresh inside the feed (the mounted list ignores a new `initial` anyway, its reducer starts once). A document request, a navigation from another page, or an unreadable header still reads. Why that can't lose the list: on a navigation inside the feed Next reuses the mounted layout's cache node (`ppr-navigations.js`, `reuseSharedCacheNode`), so the prefetched layout without `initial` is never swapped in; where it is used (a later navigation from outside the feed to that same URL within 5 min) `FeedList` mounts without `initial` and fetches its first page, and on a refresh React keeps the same `FeedList` instance and state.
- **Staleness guard.** Next keeps a prefetched or visited page in its client cache for minutes, so server data can be old when shown. Both the page and the layout stamp `loadedAt`; `isStale` (`lib/freshness.ts`, `STALE_AFTER_MS` = 10 s; a browser clock more than 5 s off also reads as stale) decides on mount.
  - Match page: what to show and whether to check are pure functions in `components/feed/match-status.ts` (tested): `openView` (status to show first, stale or not, mark seen or not) and `serverView` (what to do with a server answer). Stale: the data shows at once and `MatchDetail` re-reads `GET /api/v1/feed/:matchId` once (status, withdrawn). A server status that differs from the one shown is shown and announced (`announceMatchStatus`), so the list row and this tab's memory follow; a change made on this page since always wins; a failed check keeps what is shown. The composer re-reads `GET /api/v1/drafts?matchId=` (versions and sent kinds).
  - **Conditional "seen".** Opening a match whose shown status is "new" posts `{ status: "seen", onlyIfNew: true }`; the route calls `markMatchSeen` (`packages/db/src/matches.ts`), which updates only `where status = 'new'` (row lock, one `seen` event, like `setMatchStatus`) and returns the status the match has afterwards, which the page syncs to. Old "new" data can no longer overwrite Saved, Dismissed or Replied, from any tab. `onlyIfNew` with another status is a 400. Restore and Unsave still send a plain "seen".
  - **Hydration.** The stale flag comes from the browser clock, so it is read with `useSyncExternalStore` (server snapshot: `serverOpenView`, never stale; client snapshot computed once per mount). Hydration uses the server's value and React switches to the client's right after, so there is no mismatch; the background check runs once. The composer's `confirmed` is derived on every render (`isConfirmed`) from `revalidate`, not fixed in a `useState`.
  - Merge, not replace (`mergeVersions`, `mergeSent` in `composer-state.ts`): by id the further-along status wins (pending < running < done), failed versions drop, on a tie the fresher list wins; sent is a union. The composer also keeps the newest versions it has seen per match in a module-level map (`versionsByMatch`, beside the edits and sent maps), merged with the page's data on mount and on every revalidation, so a draft started in this browser can't vanish behind older server data.
  - Until the server has confirmed (`confirmed`), "Draft reply" never shows (`canOfferDraft`; a skeleton shows instead when nothing is known), and rewrites and "I posted this" are disabled (`actionsBlocked`). If the check fails it stays unconfirmed and shows "Couldn't check for newer versions." with a Retry button. A draft is never started and credits are never spent without a click.
  - Per-tab memories are capped at 200 matches, oldest first (`setBounded`, `lib/bounded-map.ts`): the composer's one map (`rememberDraftState`: edits, sent, versions) never drops a match with edits not marked sent, and the status map never drops the open match.
  - List, stale: one quiet `refresh()` on mount; newer gigs wait behind the "N new gigs" bar and existing rows take fresh scores and statuses. A refresh also drops rows (and waiting new gigs) that fall within the fresh page's range but are missing from it (dismissed in another tab, withdrawn): rows sorting at or before the fresh page's last item, or every row when the fresh page has no next cursor. Rows past it belong to later pages and stay; nothing is added or reordered.
  - List from back/forward: the layout can come back from Next's cache with an old `initial`. `startState` applies this tab's known statuses (`knownStatus`): rows this tab dismissed after the page was loaded stay out, and a status set since shows instead of the page's.
- Relative times in rows have `suppressHydrationWarning`, as on the match page.

## Instant open and prefetch on intent (2026-10-21)

- **Preview while a match loads.** `feed/[matchId]/loading.tsx` renders `MatchPreview` (`components/feed/match-preview.tsx`) in the detail pane (on a phone, as its own screen with the back link). It reads the match id with `useParams` and the list's copy from `match-preview-store.ts` (a module-level map, up to 500 matches, filled by `FeedList` with every row it loads, refreshes or inserts; read with `useSyncExternalStore`, empty on the server and during hydration). With a copy it shows the real header, red flags, "The post asks you to", why it matched and the summary (`MatchHeader`, `MatchNotes`, `BackToMatches` in `match-header.tsx`, shared with `MatchDetail`); without one (alert link, reload, overview, tracker) it is all skeleton. The post text and the composer are skeletons, the actions are disabled, the article is `aria-busy`. The real page replaces the whole boundary, so no list data outlives it.
- **Filters without a server trip.** A filter change uses `window.history.replaceState` (Next 16 syncs `usePathname`/`useSearchParams` with the native history API; `docs/01-app/01-getting-started/04-linking-and-navigating.md`, "Native History API") instead of `router.replace`, so an open match page isn't fetched and rendered again (it was 4 queries, a preview flash and a composer remount). The list's filters, query and generation counter follow `useSearchParams` as before.
- **Prefetch on intent** (`prefetch-intent.ts`, pure and tested with fake timers; `use-prefetch-intent.ts`, the hook used by `MatchRow` and the `j`/`k` handler in `FeedList`):
  - Intent: a mouse pointer resting on a row for 150 ms (`pointerType === "mouse"`, cancelled on leave, on click, and when the row unmounts), or a `j`/`k` selection staying on a row 150 ms (the next `j`/`k` or the list unmounting cancels it). Never on scroll or visibility; never the open match.
  - Full prefetch: `router.prefetch(href, { kind: PrefetchKind.FULL })`. `PrefetchKind` comes from an internal `next/dist/...` path on purpose: an upgrade that moves it fails the build loudly; if Next removes it, switch to a `<Link prefetch>` turned on at intent. In Next 16.3 the default kind is `auto`, which for this dynamic route would only fetch the loading state; `FULL` caches the whole page for `staleTimes.static` (5 min), so the click renders from the client cache. Keyed by the row's href (filters included, as Next caches per URL).
  - Dedupe: not again within 30 s, and not while Next still holds it (5 min) unless Next calls `onInvalidate`.
  - Load: at most 10 a sliding minute per tab, 2 at once (`router.prefetch` has no completion signal, so each holds a slot 1.5 s); only the newest intent waits for a slot.
  - Device: only when `matchMedia("(hover: hover) and (pointer: fine)")` matches and `navigator.connection.saveData` isn't true, checked at each intent.
  - No side effects: the match page and the feed layout only read during render (session, profile, feed page, match, credits, versions, sent kinds); "seen" is marked by `MatchDetail`'s effect after mount, drafts only on a click. Page requests don't touch Redis (the proxy has no rate limit).
- **Next's automatic prefetch is off for links into the feed** (with `loading.tsx` it would fetch the loading state of every visible row, and from outside the feed it would render the feed layout, which reads the list): match rows, the dashboard's newest matches and "See all matches", the tracker titles, the Matches nav item (sidebar and phone tab bar, via `prefetch: false` in `app-nav.ts`), the setup checklist (all three are dynamic pages without a loading state, so Next would fetch no data for them anyway) and the back links on the match page and its preview. Other nav items and the composer's `/settings` link keep the default.
- **Two holes in the staleness guard, found and fixed for cached pages younger than 10 s** (a prefetch, or back/forward):
  - Status: a page that still says "new" would mark the match "seen" again, overwriting a Save, Dismiss or Replied set in this tab since. `announceMatchStatus` records the last status this tab set or learned per match with its time (`knownStatus` in `feed-events.ts`, `{ status, at }`). The page prefers it only when `at` is later than the page's `loadedAt` minus 5 s of clock skew (`localIsNewer`), so a status from long ago can't override fresher server data; when it wins and differs from the page's, the page counts as stale and asks the server. The server's conditional "seen" (above) closes the rest.
  - Drafts: after "Draft reply" the composer had no version until the first poll (1.5 s); leaving and coming back to a cached page within that time offered "Draft reply" again (the server would return the same draft, so no double charge, but the button was wrong). A pending stand-in (`pendingFirstDraft`) now goes into the versions at once.

## Decisions

- **Feed polling (open):** no Redis cache for the feed (discussed 2026-10-20; at 1,000 users a cache roughly doubles the Upstash bill to save sub-millisecond indexed queries). The list refreshes on tab focus and on demand. A timed `since` poll (60 s, visible tab only) is the recommended next step, waiting for the user's go-ahead.
- Routes are top-level (`/feed`, `/tracker`, `/settings`) because Telegram buttons already link to `/feed/<id>`.
- The overview counts **gigs**, not reply rows (a comment and a DM on one gig count once).
- Opening a match marks it `seen` on the match page only (the list just clears the dot), so alert links mark it too.

## Nav links don't prefetch

Checked in a production build (2026-10-21): with Next's default, every page load prefetched the Overview, Tracker, Profile and Settings pages from the sidebar, the phone tab bar and the logo, building each page and running its queries for nothing. All nav and logo links now use `prefetch={false}` (`components/app/app-nav.ts`, `app-nav-links.tsx`, `mobile-tab-bar.tsx`, `app-sidebar.tsx`, the `(app)` and `(onboarding)` layouts). In the same check: no row prefetches on load or scroll, none on a quick pass, one on a 150 ms rest (a route-tree request plus the page), none on a second hover, and the click opened the match from the cache in about 50 ms with no request.

## Known gaps

- Score-0 broad matches ("Broad match: shares your job type") fill the All view; hiding very low scores is open.
- The tracker, settings and profile pages haven't had the real-data browser pass yet.
- A saved alert minimum score below 50 shows a note instead of a slider position.
- The onboarding review-step copy still says matches are emailed (waiting for approval).
- The feed `since` poll (above).
- A match id that doesn't exist answers with status 200, not 404: `feed/[matchId]/loading.tsx` streams the preview first, so the status is sent before the page calls `notFound()` (the not-found UI still shows). Accepted; matters only for crawlers, and the app is signed-in only.
- The layout's list read is skipped by reading Next's internal `next-router-state-tree` header; if a Next upgrade changes its format the read simply runs again (one wasted query per prefetch that renders the layout), it never breaks the list.
- A prefetched match page used for a navigation from outside the feed (same URL, within 5 min) brings a layout without `initial`: the list shows its skeleton and fetches the first page.
- A refresh answered after a status change made while it was in flight (e.g. a restore) can drop that row until the next refresh.

## Endpoint coverage

Every `/api/v1` endpoint now has a UI caller except `GET /me` (the settings page reads the email from the session server-side), `/health` (ops) and `/dev/session` (dev login, already used). New this build: `GET /api/v1/feed/:matchId`.
