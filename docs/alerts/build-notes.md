# Alerts build notes

Running notes while building the phases in `plan/`. They feed `conclusion.md` at the end.

## Phase 1: schema and pure rules (2026-10-20)

- Migration `0015_alerts.sql` is generated by drizzle-kit, with one hand-added line before it was ever applied: `UPDATE "matches" SET "alert_outcome" = 'skipped_backfill'`, so matches that exist when alerts ship are never alerted. `alerts-schema.test.ts` proves it on a throwaway database (migrate to 0014, insert a match, migrate to 0015); the test fails if the line is removed.
- Extra index not in the plan: `alert_deliveries_user_idx` on `user_id`, used when a disabled channel fails that user's pending rows.
- `telegram_link_tokens.token_hash` has a check for 64 lowercase hex characters, so a raw token can never be stored by mistake.
- `telegramAlert(items, appOrigin, now)` takes `now` (for "posted 6 min ago"), strips a leading `[Hiring]` tag from titles, and cuts titles at 120 characters. Several matches: each title links to its draft page and one "Open Redlance" button goes to `/feed`.
- `startOfLocalDay` falls back to UTC for an unknown zone (profiles store a validated zone, so this is a guard only).
- Tests: core 305 (+23), db 301 (+11), worker 561, web 377. Typecheck and lint clean.

## Phase 2: matcher origin (2026-10-20)

- `upsertMatches(db, rows, { origin })` takes a required `origin`, so every caller has to say whether its rows are from a new post or a backfill. The matcher passes `post` from `matchPost` and `backfill` from `runRematch` (only onboarding's backfill requests a re-match now that profile edits don't).
- New inserts are detected with `xmax = 0` in `returning`; `NOTIFY match_alerts` fires only for a `post` batch that inserted at least one row.
- Test overrides in `matcher.test.ts` forward the caller's options instead of hard-coding one.
- Tests: db 304 (+3), worker 561 (matcher tests 1 and 9 now check the alert outcome), web 377.

## Phase 3: the alert queue (2026-10-20)

- `packages/db/src/alerts.ts` holds all the queue SQL (routing batch, claims, completes, fails, linking, upkeep, stats).
- The routing batch locks each user with `pg_advisory_xact_lock` (users sorted, so two routers can't deadlock), so concurrent routers can't exceed the daily cap.
- Claims skip users who already have a delivery in `sending`: one message per user at a time. The sender's 403 test found this.
- The linking upsert disables another account's link to the same chat, with reason `user_stop`.

## Phase 4: the router (2026-10-20)

- Built by a Sonnet subagent.
- Routing 1,000 matches across 100 users takes about 107 ms (5 batches of 200).

## Phase 5: Telegram client, sender and bot (2026-10-20)

- The client is fetch-based. Its errors never carry the URL or the token.
- The sender paces itself with an evenly spaced limiter (40 ms between sends at 25 a second) plus 1.1 s spacing per chat.
- A circuit breaker opens after 5 outages in a row (60 s, doubling, up to 15 min).
- Bot replies are plain text.
- A 401 or 404 from Telegram becomes `TG_UNAUTHORIZED`: retryable, and the attempt is not counted, so a bad token never kills alerts.

## Phase 6: web API (2026-10-20)

- Built by a Sonnet subagent.
- Without a profile the API answers 403 "Finish onboarding first". With no bot configured it answers 503 `TELEGRAM_UNAVAILABLE`.
- `DELETE` reuses the alerts-settings rate-limit bucket.
- The copy in `review-step.tsx` is NOT changed yet (waiting for the user).

## Phase 7: wiring, env, upkeep, CLIs (2026-10-20)

- Env (`apps/worker/src/env.ts`): `ALERTS_ENABLED` (default true), `TELEGRAM_BOT_TOKEN` (shape-checked; the error message never contains the value), `TELEGRAM_BOT_USERNAME`, `TELEGRAM_MAX_PER_SECOND` (1-30, 25), `ALERT_MAX_AGE_HOURS` (1-168, 24), `APP_ORIGIN` (http(s) URL, normalised to its origin; required when a token is set). The worker had no `APP_ORIGIN` before, so this is new there.
- `createAlertsFromEnv` (`apps/worker/src/alerts/index.ts`) returns null when disabled, builds the router always, and the sender and bot only with a token. It logs one "alerts started" line saying which parts run. The bot's lock key is `redlance:telegram-bot`. The listeners and the lock use their own connections.
- `index.ts` starts alerts after the voice updater, stops them with the others (the sender gets 3 s to finish sends, inside the existing shutdown budget), adds `alerts` and `telegram` to the "worker started" line, and the pool `max` goes up by 2.
- Upkeep: a `prune-alerts` step calls `pruneAlerts` (failed deliveries over 30 days, link tokens expired over a day) and logs counts when above 0. It has no test of its own (upkeep has none; `pruneAlerts` is tested in `packages/db`).
- `npm run alerts:status -w @redlance/worker`: backlog, outcomes in 24 h, deliveries pending/sending/failed, oldest pending `run_after`, sent in 24 h, linked/disabled channels. Counts only.
- `npm run alerts:test -w @redlance/worker -- --user <uuid>` (`scripts/alert-test.ts`): refuses unless `APP_ENV` is local or test. Inserts a fake fresh hiring post (marked already matched, so the real matcher ignores it), its analysis, and a match scored 90 with `alert_outcome` null, then NOTIFYs `match_alerts` and prints the match id. The user needs a profile.

## Review fixes (2026-10-20)

- **M1 (double send after a long 429 pause):** new `touchDeliveries(db, rows)` in `packages/db/src/alerts.ts`: one fenced update that refreshes `locked_at` only if every row is still `sending` with the claim's attempts, and returns false (touching nothing) otherwise. The sender calls it after the limiter and spacing waits, right before `sendMessage`. On false (or a DB error) it logs "claim lost before send", does not send, and gives back whatever is still its own (`CLAIM_LOST`, attempt not used, retry now; the fence makes this a no-op for rows another sender owns). No lock refresh while waiting. Tests: db (refresh keeps the sweep away; false after a sweep and after a re-claim), sender (two groups, the sweep re-queues the waiting one during a 1 s 429 pause: exactly one send per match; a stolen claim is never sent).
- **L1 (shutdown during a long wait):** `Clock.sleep`, `limiter.take()` and `spacing.wait()` take an `AbortSignal` and return at once when it aborts. `sender.stop()` aborts it, so waiting groups reach the `SHUTDOWN` give-back (attempt not used, retry now) before stop resolves. Tests: pace (abort mid-pause, pre-aborted, spacing) and sender (100 s pacer wait, 200 ms grace: stop returns fast and the row is pending with `SHUTDOWN`).
- **L4 (bot error reply):** `handle()` now catches its own errors, logs "telegram update failed" (codes only) and replies once, in plain text, "Something went wrong. Please try the link again in a minute." (`BOT_REPLIES.failed`) to private chats. The poll loop just calls it. Tests: direct and in the poll loop (the loop carries on).
- **L5 (`relinked`):** `CHANNEL_DISABLED_REASONS` gains `relinked` (core + the schema mirror); migration `0016_alert_relinked.sql` (drizzle-generated, renamed, journal tag fixed) swaps the check constraint; applied to the dev db. `useTelegramLinkToken` disables the old account with `relinked`. The web API passes `disabledReason` through as a string, so the UI may want copy for it.
- **L7 (pool):** the worker pool bump for alerts is +5 (was +2), with a comment in `apps/worker/src/index.ts`.
- **L8 (bot replies and the limiter):** `createAlertsFromEnv` builds one limiter from `TELEGRAM_MAX_PER_SECOND` and passes it to the sender (`limiter` dep) and the bot (`limiter` dep, `take()` before every `sendText`). Both still build or skip their own when it isn't passed (tests). Test: the bot takes a slot before each reply.
- **L9:** `useTelegramLinkToken` inserts a uuid v7 made in JS (`uuid`'s `v7`), not `gen_random_uuid()`. Test checks the version nibble.
- **Empty keyboard:** core's `telegramAlert` can return `{ inline_keyboard: [] }` for a localhost or IP `APP_ORIGIN`; the sender now leaves `replyMarkup` out unless some row has a button. Test with `http://localhost:3001` and a 3-match message.
